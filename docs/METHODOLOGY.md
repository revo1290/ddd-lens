# 評価方法

## 1. DDD適用妥当性

適用度とは別に、次を0〜4で確認します。

- 業務ルールの複雑性
- 事業上の差別化
- 変更頻度・不確実性
- 外部・組織間統合の複雑性
- ドメイン専門家へのアクセス（これは価値ではなく実行可能性）

前4項目の平均で `適用推奨`、`選択的適用`、`適用非推奨` を出します。3項目未満しか確認できなければ判定を保留します。

このゲートが必要なのは、DDDがパターン集ではなく、複雑なドメインをモデルで扱うための方法だからです。単純で安定した汎用CRUDに集約、Repository、CQRSを足しても、通常は費用だけが増えます。

## 2. 適用度

5軸15項目を0〜4で評価します。

| 値 | 意味 |
| ---: | --- |
| 0 | 必要な場所にない、または害が確認できる |
| 1 | 名前・形式はあるが、意思決定や振る舞いが伴わない |
| 2 | 局所的には機能するが、一貫性がない、または人に依存する |
| 3 | 対象範囲で明示・反復・検証される |
| 4 | 定期的に計測・見直され、モデル進化の実績がある |
| 未評価 | 根拠不足。0点にも合格にも数えない |
| N/A | 理由を明記して適用対象外 |

軸ごとの重みは戦略設計30%、言語20%、モデル20%、境界20%、進化10%です。項目内は定義された重みで平均します。

## 3. 根拠カバレッジ

評価済み項目を確信度で `high=1.0`、`medium=0.6`、`low=0.25` と加重し、すべての適用可能項目で割ります。40%未満では総合値が計算できても、段階ラベルを付けません。キーワード一致だけで見かけ上のカバレッジが高くならないための措置です。

高得点・低カバレッジは「良い状態」ではなく「見えた範囲は良い」です。この区別を消さないでください。

## 4. 確信度

| 確信度 | 目安 |
| --- | --- |
| high | 実行可能な制約が直接証明する、または独立した強い根拠が一致する |
| medium | 現行コード＋テスト、または複数の現行資料・関係者証言が一致する |
| low | 名前、ディレクトリ、正規表現、一つの資料、静的ヒューリスティック |

CLIの自動判定は原則 `low`、明白な技術依存など局所的な事実のみ `medium` です。

## 5. 誤用防止

- 組織やチーム間の人事評価に使わない
- スコア目標を設定しない
- パターン導入数をKPIにしない
- 低カバレッジの総合点を経営指標にしない
- `未評価` を欠陥件数として扱わない

推奨用途は、四半期ごとの同一プロジェクトレビュー、境界変更の前後比較、改善仮説の優先順位付けです。
